# AI 서버 회고와 취업 설명 준비

기준: 2026-09-14, `develop@406099c`. 이 문서는 [개발 기록](DEVELOPMENT_HISTORY.md)과 [근거 목록](EVIDENCE.md)을 짧은 설명으로 연결한다. 문장을 길게 외우기보다 실제 코드의 선택 이유·경계·한계를 설명할 수 있도록 준비한다.

## 1. 이 서버에서 배운 점

### AI 품질은 모델 호출 성공만으로 결정되지 않는다

센서 단위와 시간 범위가 잘못 결합되면 모델이 정상 응답해도 잘못된 설명을 만들 수 있다. 입력의 의미와 결측·실패를 구분하는 계약이 먼저 필요했다. 출력도 형식, 근거 일치, 사용자 유용성을 나누어 평가해야 한다.

### 서비스 사이의 성공 조건을 나누어야 한다

피드백 저장, Outbox 발행 완료, Notification 저장, 외부 채널 발송, 사용자 화면 접근은 각각 다른 단계다. 한 단계의 성공을 전체 성공으로 확대하지 않고 상태와 증거를 따로 남기는 방법을 익혔다.

### 느린 외부 호출과 DB의 책임을 분리할 수 있다

데이터 수집·Vision·LLM 통신 중 DB 트랜잭션을 유지하지 않고, 저장에 필요한 짧은 구간만 별도 트랜잭션으로 묶었다. 동시성에서는 선조회만 믿지 않고 DB 유일성을 최종 기준으로 삼는 이유를 배웠다.

### 복구 가능한 상태와 멱등성도 기능이다

실패가 생겼을 때 처음부터 모든 대상을 다시 생성하지 않고, 저장한 피드백과 사진 분석 결과를 재사용한다. 발행 의도를 Outbox에 보존하고 시도와 이벤트의 정체성을 구분했다. 단, 이 구조도 중복 외부 호출·중복 발행 가능성을 완전히 없애는 것은 아니다.

### 내가 만든 기능과 팀이 완성한 결과는 구분해야 한다

일일 피드백의 생성·발행 측을 구현했다고 Notification이나 프론트 전체를 만든 것은 아니다. 팀원의 ADMIN·다운로드·화면 후속 변경을 함께 기록해야 내 실제 기여가 정확히 드러난다.

## 2. 잘한 선택과 아쉬운 점

| 항목 | 남길 판단 | 아직 과장하면 안 되는 것 |
|---|---|---|
| 데이터 계약 | 재배지·EUI·센서 타입·단위를 함께 취급하고 필수 `unit`을 호출부·테스트까지 반영 | 모든 통합 오류의 근본 원인을 한 번에 해결 |
| 입력 정제 | 원본 Snapshot과 외부 전송용 복사본을 분리 | 모든 개인정보·프롬프트 인젝션을 완전 차단 |
| 출력 검증 | 제목·본문 존재·금지 정보 등을 코드에서 확인 | 환각·수치 오류·설명 부실이 모두 제거 |
| 사진 상태 | 없음·미탐지·불확실·호출 실패를 구분 | 분석 실패한 재배지도 무조건 새 피드백 저장 |
| Outbox | 짧은 원자 저장과 별도 발행·복구 | DB와 Broker의 분산 트랜잭션 또는 exactly-once |
| 운영 확인 | 특정 실행의 배치·Outbox·Notification 결과 대조 | 현재도 모든 사용자에게 정상 전달 |

아쉬웠던 점은 자료가 코드·대화·스크린샷에 흩어져 최초 증상과 복구 주체를 완전히 재구성하기 어려웠다는 것이다. 다음 프로젝트에서는 사건별로 재현 입력, 버전, 가설, 변경, 단계별 결과를 함께 남기는 것이 좋다.

| P0 | 실제로 부실하다는 Vision 문장 확보 | 모델 출력 부족과 LLM 활용 부족을 구분해야 함 | 해당 본문·정제한 Context·사진·생성 시각·배포 버전 |

| P1 | DB 동시성 실증 | Mock 테스트와 실제 DB 트랜잭션은 다름 | 실제 UNIQUE 제약 확인, 병렬 저장·선점 테스트 결과 |

| P2 | 대표 사진 선택 기준 | 현재 최대 한 장의 응답 계약만 확인됨 | Cultivation 담당자와 선정·중복·누락 기준 합의 |
| P2 | 내부 인증·이미지 계약 강화 | 임시 ADMIN 헤더와 이미지 허용 origin 경계가 있음 | 신뢰된 호출자 인증, 주소 정책·만료 시나리오 계약 테스트 |
| P2 | 최신 공통 설정·이벤트 변경 정리 | 기준 revision 이후 변경을 완료로 추정할 수 없음 | 해당 PR·diff·테스트·배포·양측 이벤트 계약 |
| P2 | 효율의 실제 측정 | 재사용 구조가 있어도 비용·시간 절감률은 아직 없음 | 같은 조건의 호출 수·지연·LLM 사용량 비교 |

Vision 개선에서 문장 분량만 늘리지 않는다. 모델이 제공하지 않는 병명·병변 위치·원인·수확 시점·개체별 병해 수는 작성하지 않는다. 실제 사진과 분석 대상 영역을 보여주더라도 영역을 병변 위치로 오해하게 하면 안 된다.

## 4. 백엔드 취업 설명 소재

### 소재 A. API 계약 누락을 호출 경로 전체에서 수정

- **상황:** 센서 통계 수집을 다른 서버의 API에 의존했다.
- **문제:** 요청에 필수 단위가 누락되어 선언·호출·실제 서버 계약이 어긋났다.
- **행동:** Feign의 `unit` 인자, 채널 단위 전달, 테스트 stub을 함께 수정했다. 개인 커밋은 `cde30d4`다.
- **검증 범위:** diff·현재 호출부·테스트 시나리오를 확인했고 이후 제공된 배치 성공 기록이 있다. 같은 시기 의존 서버 재시작도 있어 전체 복구를 이 수정 하나의 성과로 설명하지 않는다.
- **면접 질문:** “Mock 테스트가 있었는데 왜 발견하지 못했나요?” 실제 제공 API의 필수 파라미터까지 테스트 계약에 포함해야 하는 이유를 설명한다.

### 소재 B. 외부 호출과 저장 트랜잭션 분리

- **상황:** 외부 API와 모델 응답은 지연·실패할 수 있다.
- **선택:** 수집·생성은 `NOT_SUPPORTED`, 피드백·Outbox 저장은 별도 Bean의 `REQUIRES_NEW`로 분리했다.
- **설계 이유:** 외부 응답 대기 중 DB 연결·행 잠금을 장시간 유지하지 않고, 저장 경쟁에서 롤백 후 기존 행을 안전하게 재조회하기 위해서다.
- **한계:** 동시에 선조회를 통과한 두 실행의 모델 호출까지 막지는 못한다. 소스 애너테이션과 Mock 테스트는 운영 동시성 실험과 다르다.
- **면접 질문:** “왜 같은 클래스 내부 메서드에 애너테이션을 붙이는 것으로 끝내지 않았나요?” Spring 프록시 경계를 통과하도록 별도 Bean을 둔 이유를 설명한다.

### 소재 C. Outbox에서 ‘완료’의 의미를 좁혀 정의

- **상황:** 피드백만 저장되고 알림이 발행되지 않거나, 발행은 됐지만 상태 기록이 실패할 수 있다.
- **선택:** 발행 의도를 피드백과 함께 저장하고, Relay에서 Broker ACK와 미반환 조건을 검사했다. 실패는 재시도·최종 실패·stale 복구 상태로 구분했다.
- **검증 범위:** 과거 제공 자료에서 신규 Outbox 11건 PUBLISHED 및 대응 Notification 저장을 확인했다. 이 숫자는 특정 실행 사례다.
- **한계:** 발행 후 상태 저장 전에 종료되면 재발행될 수 있다. 소비 측 eventId 중복 처리와 결합하는 at-least-once 구조다.
- **면접 질문:** “ACK면 왜 다시 보낼 수 있나요?” Broker 수신과 AI DB 상태 기록은 한 트랜잭션이 아니라는 틈을 설명한다.

### 소재 D. AI 결과를 저장 가능한 서비스 계약으로 다루기

- **상황:** 구조가 다른 센서·환경·알림·Vision 자료를 LLM 설명으로 연결해야 했다.
- **선택:** 입력 Context를 정제하고 프롬프트와 출력 Validator를 분리했다. 사진 없음과 실패, 0과 null, 원본 상태와 모델 점수를 구분했다.
- **검증 범위:** 현재 상태별 처리·형식·금지정보 테스트 시나리오가 있다.
- **한계:** 실제 Vision 피드백의 유용성 평가가 남아 있다. “LLM 응답을 검증했다”와 “환각을 없앴다”는 다르다.
- **면접 질문:** “AI를 왜 사용했나요?” 계산은 코드, 사진 판단은 Vision, 다양한 결과를 사용자가 읽을 설명으로 구성하는 역할은 LLM에 둔 이유와 규칙 템플릿 대안의 존재를 함께 설명한다.

### 짧은 이력서 문장 후보

> Spring AI 기반 일일 피드백의 데이터 수집·입출력 검증·멱등 저장을 구현하고, Outbox의 발행 확인·재시도 흐름을 연계했습니다.

> 센서 조회의 필수 단위 파라미터 누락을 Feign 선언·호출부·테스트까지 수정하고, 배치·발행·소비 측 저장을 나누어 통합 결과를 확인했습니다.

실제로 본인이 설명 가능한 범위를 선택한다. “AI 서버 전체 단독 개발”, “알림 유실 0%”, “처리시간 몇 배 개선”을 현재 증거에 추가하지 않는다.

## 5. 내가 직접 확인하고 보완할 목록

- [ ] 가장 먼저 문제를 발견한 실제 로그와 최초 재현 조건을 보관했다.
- [ ] API 제공자와 변경을 합의한 PR·대화·요구사항을 연결했다.
- [ ] 개인 변경과 이후 팀원 변경을 구분했다.
- [ ] `NOT_SUPPORTED`, `REQUIRES_NEW`, UNIQUE, rollback 이후 재조회 흐름을 코드 없이 말할 수 있다.
- [ ] Broker publisher confirm, mandatory return, consumer 처리, 외부 발송을 구분할 수 있다.
- [ ] eventId와 publicationAttemptId의 차이를 설명할 수 있다.
- [ ] 사진 없음과 분석 실패 시 해당 재배지 배치 결과가 어떻게 달라지는지 설명할 수 있다.
- [ ] rolling 집계점 통계와 달력 날짜 원시 통계가 다르다는 점을 설명할 수 있다.
- [ ] 기존 결과 재사용 때문에 사진·프롬프트 변경이 자동 반영되지 않을 수 있음을 안다.
- [ ] 실제 구현·테스트 시나리오·실행 기록·현재 배포를 섞어 말하지 않는다.
- [ ] 외부 제출에 사용할 로그·사진·Context에서 개인정보·내부 연결 정보를 제거했다.
- [ ] 사용자 유용성 개선이 아직 제안이면 완료 성과로 쓰지 않는다.
