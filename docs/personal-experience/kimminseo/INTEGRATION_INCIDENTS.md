# AI 연동 과정의 트러블슈팅과 협업 사건

이 문서는 사용자가 제공한 로그·화면과 확인 가능한 Git 변경을 연결한다. **증상 확인, 원인 가설, 실제 조치, 결과 확인을 구분**하며 여러 사건을 하나의 해결 성과로 합치지 않는다. 배치 내부 사건은 [개발 이력](DEVELOPMENT_HISTORY.md)에, 전체 문서의 확인 기준은 [README](README.md)에 정리했다. 아래에는 AI 결과가 실제 화면과 알림으로 이어지는 과정에서 함께 마주친 의존 서비스·프론트·발표 사건도 포함한다. 이 문서에 등장하는 다른 서비스 전체가 김민서의 구현 범위라는 뜻은 아니다.

## I01. 데이터가 존재해도 사용자에게 조회 권한이 없을 수 있었다

- **시기·상태:** 2026-09-04 전후 / [대화 증거]. 해당 재배 소유자 확인과 내부 직접 조회 성공, 브라우저 권한 문제 최종 원인·해결은 별도.
- **증상:** 재배 서버에 ‘접근 권한이 없는 재배’ 로그가 나타났고, 이후 프론트 피드백 화면에서도403이 보였다.
- **확인한 사실:** 관리자 자격을 사용한 내부 멤버 조회로 OWNER를 확인했고, 그 소유자 ID로 재배 상세 조회 시 OWNER 응답을 얻었다.
- **의미:** 재배 데이터가 없거나 모든 사용자에게 서버가 실패한 상황과, 특정 요청자의 접근 권한 문제는 다르다.
- **불확실한 부분:** 브라우저 세션의 실제 사용자와 전달된 인증 정보를 확보하지 못했다. 소유자 내부 조회 성공이 브라우저 피드백 API의 인증·인가까지 증명하지 않는다.
- **설계/연동 조치:** Front `ebe8363`에서 Feign403을403으로 전달하고, 원본 `detail` 문구를 읽는 처리 등을 추가한 기록이 있다. 이는 상태를 정확히 전달하는 개선이지 무조건 접근을 허용한 변경이 아니다.
- **배운 점:** ‘로그인됨’, ‘재배 조회 가능’, ‘해당 피드백 조회 가능’을 별도로 확인한다. 내부 진단용 사용자 헤더를 프론트 인증 우회 방식으로 사용하면 안 된다.
- **안전한 경험 문장:** “조회 장애를 데이터 존재 여부와 사용자 접근 권한으로 나눠 확인하고, 프론트가 실제 오류 상태를 유지하도록 연동을 보완했습니다.”

## I02. 센서 통계 요청에서 단위가 계약에 포함되지 않았다

- **시기·상태:** 2026-09-04 / [기록 확인] AI `cde30d4`.
- **확인한 변경:** 통계 조회 Feign 인터페이스에 `@RequestParam("unit")`을 추가하고 호출부와 테스트 인자를 맞췄다.
- **문제의 핵심:** 같은 센서 타입이어도 단위가 다르면 다른 채널/통계 계약이다. `sensorType`만 전달하는 것은 충분하지 않다.
- **검증 근거:** 변경 diff와 테스트 수정 기록. 이후 배치 성공 로그는 I04에 별도로 남긴다.
- **인과관계 한계:** 당시 최초 실패 전체 원 로그는 확보하지 못했다. 같은 시간대에 재배 서버 OOM과 재시작도 있었으므로 ‘unit 한 줄 수정으로 전체 장애를 해결했다’거나 개선율을 주장하지 않는다.
- **배운 점:** 제공 API, 호출 인터페이스, 실제 인자, 테스트 대역이 동일 계약을 사용해야 한다.

## I03. 재배 서버 Java heap OOM이 다른 서비스의 기능 검증까지 막았다

- **시기·상태:** 제공 로그 UTC 2026-09-03 18:46경, KST 9월4일 새벽 / [대화 증거]. 재시작 롤아웃 완료, 근본 원인·재발 방지는 미확인.
- **증상:** HTTP Poller, Redis 관련 스레드, AMQP 연결 등 여러 곳에서 `OutOfMemoryError: Java heap space`가 나타났다.
- **확인한 스택:** 센서 캐시 스케줄러→Redis 캐시 append→hash 삭제용 키 직렬화 경로에서 할당 실패가 보였다.
- **판단:** 이 경로는 메모리를 할당하지 못한 지점이다. 이것만으로 해당 메서드가 메모리 누수의 발생원이라고 단정할 수 없다. Redis/JPA 초기화 안내나 open-in-view 경고도 이 OOM의 원인이라고 확인되지 않았다.
- **사용자가 실행한 조치:** `cultivation-server` Deployment를 재시작했고 rollout 성공 출력을 제공했다.
- **후속 결과:** 이후 수동 일일 피드백 배치가 성공했다. 의존 서비스 상태 회복과 배치 검증을 연결해 볼 수 있지만, OOM 해결을 모델 수정 성과로 쓰지 않는다.
- **남은 일:** 메모리 사용 추이, JVM heap 설정·컨테이너 제한, 캐시 크기/삭제 대상 규모, heap dump 등 원인 자료가 필요하다. 이번 문서화에서 운영 조사·재시작을 실행하지 않았다.
- **배운 점:** AI 기능 실패가 LLM이나 모델 자체의 실패일 필요는 없다. 서비스 의존 경로와 프로세스 건강 상태부터 나눠 본다.

## I04. 로그 일부만 보였지만 DB 대조로 생성·발행·알림 저장을 확인했다

- **시기·상태:** 2026-09-04 / [대화 증거]. 해당 실행의 배치·DB 상태 확인.
- **실행:** 기존 CronJob으로부터 `df-unit-0904-01`이라는 수동 Job을 생성한 기록이 있다. 문서화 과정에서 이 Job을 다시 실행한 것은 아니다.
- **결과:** `feedbackDate=2026-09-03`, 대상21 / 신규11 / 기존10 / 실패0. Kubernetes Job은 Complete 1/1, 실행시간2분30초로 표시됐다.
- **로그의 불완전성:** 사용자가 붙인 Outbox 처리 로그에는6개 재배의 PUBLISHED가 보였다. 이것만으로 나머지5개가 실패했다고 판단할 수 없었다. 필터·조회기간·로그 보존 등 정확한 누락 이유는 확인하지 않았다.
- **추가 확인:** DB 화면에서 신규11개에 대응하는 Outbox가 모두 PUBLISHED, attempt_count=1, published_at 존재로 보였다. 이어서 같은 source_event_id에 대응하는 Notification 레코드11개를 확인했다.
- **증명한 것:** 해당 신규11건의 피드백 생성 이후 Outbox 완료 상태와 Notification 저장의 연결.
- **증명하지 않은 것:** 기존10건의 이번 재발행, 모든 사용자에게 외부 발송, 실제 사람이 메시지를 읽음, 링크 정상 접근, 현재도 안정적으로 운영됨.
- **주의:** attempt_count=1은 해당 Outbox 처리 기록이며 외부 전달의 정확히1회 보장이나 모든 소비자의 재시도 횟수가 아니다.
- **배운 점:** “배치 성공 → Outbox 상태 → 소비 측 저장 → 외부 발송 → 링크 접근”을 각각 검증한다. 한 단계의 성공을 전체 성공으로 확대하지 않는다.
- **취업 자료에 쓸 수 있는 수치:** “제공 실행 기록 기준 대상21건 중 신규11건 생성·기존10건 재사용·실패0건, 신규11건의 Outbox/Notification 저장 상태를 대조.”

## I05. 알림 저장과 내가 Telegram을 받는 것은 달랐다

- **시기·상태:** 2026-09-04 / [대화 증거]. 전달 경계 확인, 모든 사용자 수신 미확인.
- **증상:** Notification 레코드는 존재하지만 김민서는 Telegram 알림을 받지 못했다고 말했다. 이어 본인이 그 구독 사용자가 아니라고 설명했다.
- **DB 화면:** 조사한11개 결과 중1개는 TELEGRAM / SENT / provider_message_id가 있었고, 나머지는 delivery 관련 열이 null이었다.
- **해석:** 원본 이벤트 저장과 외부 채널 발송은 별도다. 나머지 null의 이유를 모두 ‘미구독’으로 확정할 수는 없다. 조회 조인 범위와 활성 구독·연결·발송 정책을 확인해야 한다.
- **판단:** 다른 수신 대상에게 보낸 메시지를 내가 못 받았다는 사실만으로 발송 장애라 할 수 없다. SENT도 사람이 읽었다는 증거는 아니다.
- **안전한 검증 방향:** 본인 계정에 정상 구독·채널 연결을 설정한 별도 허용된 테스트, 혹은 실제 구독자에게 수신 확인 요청. 다른 사용자의 채널 정보를 임의로 바꿔 시험하지 않는다.
- **배운 점:** 이벤트 저장, 발송 대상 선정, 공급자 전송 결과, 사람의 실제 수신을 분리해야 한다.

## I06. 명령과 출력, 실행하는 컴퓨터가 섞였다

- **시기·상태:** 2026-09-04 / [대화 증거]. 작업 중 혼동으로 기록하며 완전한 원인 추정은 하지 않는다.
- **증상:** `$`, `>`, `NAME`, `<none>` 등이 포함된 출력이 셸 입력으로 들어가 `NAME: not found`, `redirection unexpected` 등이 반복됐다. 별도로 `logs: not found`도 제시됐다.
- **확인 범위:** 출력 텍스트가 명령으로 재입력된 흔적은 분명하다. 마지막 `logs: not found`의 정확한 실행 문자열은 온전히 확보되지 않아 별도 환경 장애로 단정하지 않는다.
- **또 다른 혼동:** 로컬 Mac에서 Linux의 `systemctl` 명령을 실행하려 했고, `frontend` 하위 폴더에서 없는 `./mvnw`를 실행한 화면이 있었다.
- **개선 기준:** 명령 본문만 복사하고, 매 단계의 실행 위치를 `로컬 Mac / 원격 서버 / Kubernetes 컨텍스트 / 프로젝트 루트 / frontend`로 구분한다.
- **배운 점:** 재현 가능한 운영 메모에는 명령뿐 아니라 실행 위치·전제·기대 결과가 필요하다. 아무 출력도 없다는 현상만으로 클러스터 장애라고 단정하지 않는다.

## I07. Cloudflare1033을 애플리케이션 오류와 구분했다

- **시기·상태:** 2026-09-04 / [대화 증거]. 당시 오류 화면, 정확한 복구 조치·담당은 미확인.
- **증상:** 배포 웹 주소에서 Cloudflare Tunnel error1033 화면이 나타났다. 같은 시기 로컬 Vite 화면은 열렸다.
- **확인한 사실:** 외부 접속 경로의 오류 화면이며 로컬 정적 화면 표시만으로 배포 경로·백엔드 정상 여부를 확인할 수 없다.
- **시도 기록:** 원격 계정에서 sudo 권한 부족, 조회한 환경에서 cloudflared 서비스 unit 미존재가 보고됐다.
- **주의:** unit이 없다는 것은 그 호스트·서비스 관리 방식에서 찾지 못했다는 뜻이다. 다른 호스트나 컨테이너의 터널 운영까지 없다고 단정하지 않는다.
- **후속:** 사용자가 ‘다시 돌아왔어’, ‘로그인했어’라고 전했지만 누가 무엇을 바꿔 복구했는지는 기록에 없다.
- **배운 점:** 권한이 없는 인프라 작업은 담당자 확인이 필요하다. 이 사건을 “내가 Cloudflare 인프라를 구축하고 복구했다”는 성과로 쓰지 않는다.

## I08. 로컬 화면이 열려도 로그인·백엔드 실행은 별도였다

- **시기·상태:** 2026-09-04 / [대화 증거]. 로컬8082 리스너 종료 확인, 새 서버 정상 기동 전체 로그 미확보.
- **증상:** Vite 로그인 화면은 표시됐지만 로그인되지 않았고, Spring Front 서버 실행 시 ‘Port8082 was already in use’로 시작 실패했다.
- **조치·확인:** 사용자가 해당 프로세스를 종료한 뒤 `lsof` 확인 결과 리스너 출력이 없는 상태를 제공했다. 이후의 서버 정상 시작 전체 로그는 이 대화에 없다.
- **기타 화면:** 이미지 요청이200/304이면서 Type이 text/html로 보이는 자산 깨짐 사례도 있었다. 상태코드만 보고 이미지 로딩 성공으로 판단할 수 없었다. 자산 경로가 왜 그렇게 응답했는지는 조사 완료되지 않았다.
- **연결 시도:** 로컬과 원격 Gateway를 연결하는 SSH 포워딩 명령을 제시했지만, 성공 확인 출력이 없어 연결 완료로 기록하지 않는다. 접속 주소·계정은 이 문서에 복사하지 않는다.
- **배운 점:** 프론트 개발 서버, Spring 프론트/BFF, 원격 Gateway와 백엔드 연결은 별개의 실행 상태다. 연결 구조에 따라 로컬에서 필요한 서버가 달라지므로 모든 서비스를 무조건 중복 실행하지 않는다.

## I09. 알림 URL이 있어도 직접 진입 경로가 준비됐다는 뜻은 아니었다

- **시기·상태:** 2026-09-04 / [대화 증거 + 기록 확인]. 개인 수정·push 확인, 해당 배포본의 전체 경로 정상화는 별도 검증 필요.
- **증상:** 일일 피드백 알림에 링크가 생성됐으나, 배포 사이트에서 `/cultivations/{id}/daily-feedbacks/{date}` 직접 접근 시404가 나타났다. 로컬에서는 보고서 화면이 열리더라도403을 표시한 사례가 있었다.
- **확인한 개인 변경:** Front `ebe8363`에 다음이 포함됐다.
  - Spring 페이지 컨트롤러에 일일 피드백 딥링크를 React 앱으로 연결하는 경로 추가.
  - 프론트용 일일 피드백 API 컨트롤러·AI 클라이언트 연결·DTO 추가.
  - 재배 기본 정보가 로딩 중이거나 실패해도 피드백 조회를 진행하는 화면 경로.
  - Feign403·404, `detail` 메시지와 날짜 형식 오류 처리 및 테스트 보완.
- **개인 기여 근거:** 작성자 기록 및 실제 diff, 사용자 제공 commit/push 출력. merge 작성자라는 이유만으로 다른 팀원의 모든 변경을 본인 것으로 포함하지 않았다.

## I12. 기능은 동작하지만 Vision 피드백의 내용이 부실하다는 의견을 받았다

- **시기·상태:** 2026-09-13 / [대화 증거 + 코드 확인]. 개선 요구/진단 단계, 미구현.
- **사용자 전달:** 팀원이 일일 피드백의 Vision 설명이 부실하다고 말했다. 실제 지적 문단과 그 입력 Snapshot은 아직 제공되지 않았다.
- **코드에서 확인한 사실:**
  - 결과가 단순 한 줄로 축약되는 것이 아니라 상태·품종·탐지 수·확률·경고가 Context와 정제 과정을 거쳐 전달된다.
  - LLM 입력은 분석 JSON이며 사진 자체나 병반 위치 설명이 아님.
  - 일일 피드백에는 해당 날짜 재배당 최대1장의 결과가 들어가고 과거 사진 비교는 수집하지 않는다.
  - 프롬프트는 상태 왜곡·병명 추측을 제한하지만 설명 충실성을 고정된 구조로 강제하지 않는다.
  - 출력 검증기는 제목/본문 존재/보안 등을 검사한다. 통과가 유용한 설명이나 사실성의 충분조건은 아니다.
- **판단:** 모델 범위 부족과 사용자용 설명 구성 부족을 나눠야 한다. 분량을 늘리려고 병반·원인·수확 시점·치료법을 지어내면 안 된다.
- **제안한 개선:** 분석 근거 사진·상태, 결과의 의미와 한계, 상태별 다음 확인 행동을 연결. 분석 영역을 표시하더라도 병변 위치처럼 보이게 하지 않는다.
- **재생성 주의:** 동일 재배·날짜 피드백은 기존 결과를 반환한다. 사진을 뒤늦게 추가하거나 프롬프트를 바꾼 뒤 같은 배치를 실행해도 기존 본문이 자동으로 갱신되지 않는다. 이를 콘텐츠 개선 실패와 혼동하지 않는다.
- **미확인:** 문제의 실제 출력, 해당 입력, 사진 등록/생성 시점, 배포 프롬프트 버전. 전후 품질 개선 성과는 아직 없다.
- **배운 점:** 모델 평가, API 계약, LLM 문장 품질, 화면에서의 이해 가능성은 서로 다른 품질 기준이다.
