# AI 일일 피드백 — 데이터를 검증하고 설명·저장·알림으로 연결한 경험

> 작성 기준: 2026-09-14. 로컬 `Ai_server`의 `develop`, `406099c20ddb2d81c900fbc60c446d73f8e21fe9`를 읽기 전용으로 확인했다. 운영 서버 접속, 재배치 실행, 테스트 재실행은 하지 않았다. 이 문서는 **과거 대화에서 확인한 사건**, **현재 코드의 구현**, **향후 개선 제안**을 구분한다. 근거 상세는 [EVIDENCE.md](EVIDENCE.md)에 있다.

## 1. 이 경험을 한 문장으로 정리하면

> 여러 서비스의 센서·환경·알림·사진 분석 데이터를 검증된 Context로 조합하고, Spring AI 기반 설명 생성부터 멱등 저장과 Outbox 발행까지 일일 피드백 흐름을 연결했다.

핵심은 “LLM을 붙였다”가 아니다. **서로 다른 데이터 계약을 맞추고, 부족한 데이터와 실패를 구분하며, 생성 결과와 알림을 추적 가능한 상태로 남기는 것**이 주요 경험이다.

### 내 역할과 팀 역할

| 구분 | 근거를 바탕으로 설명할 수 있는 범위 | 확장해서 주장하면 안 되는 범위 |
|---|---|---|
| 김민서 주 담당 | Vision 결과 저장 연동, 일일 피드백 수집·생성·저장, Outbox 연계, 운영 조회 API, 센서 `unit` 전달 수정 | AI 서버 전체를 혼자 설계·개발했다고 표현 |
| 팀 기반 위의 작업 | 기존 Feign·RabbitMQ·Cultivation·Notification 계약을 사용하고 그 경계에서 통합 검증 | 인증·재배 관리·알림 발송·Gateway·인프라 전체 구현 |
| 공동 유지보수 | 초기 구현 이후 팀원이 ADMIN 조회, 이미지 다운로드 설정, 프론트 표현 등을 보완 | 현재 파일의 모든 줄을 개인의 단독 기여로 표현 |
| 별도 팀원 영역 | 챗봇, 인사이트, 임베딩/PGVector 등 | 일일 피드백용 LLM 연동 경험을 RAG 전체 구현 경험으로 확대 |

개인 구현을 뒷받침하는 커밋은 `fffa91e`, `7af231a`, `b17c1d9`, `bfff1c2`, `aefcedf`, `cde30d4`다. 커밋은 변경의 출처이지 작업시간·기여율·수작업 작성량의 증거가 아니다. AI 개발 도구의 도움을 받은 부분도 이해·검토·검증한 범위로 설명한다.

## 2. 왜 이 기능이 필요했나

사용자는 센서 숫자와 반복 알림을 따로 확인해야 했다. 사진 분석도 품종·건강 상태라는 구조화된 결과로 존재했다. 일일 피드백은 이 자료를 모아 “어떤 환경이 관찰됐는지”, “점검할 항목은 무엇인지”를 한곳에서 설명하기 위한 기능이다.

- 수치 계산과 계약 검증: 서비스 코드와 데이터베이스가 담당한다.
- 사진 판단: 별도 Vision 모델이 제공한다.
- 사용자용 설명: LLM이 제공된 자료를 근거로 작성한다.
- 제어 결정: Rule Engine 등 별도 정책의 책임이다. LLM은 장치 제어나 수확 전환을 결정하지 않는다.

“AI 없이는 절대 제공할 수 없는 기능”이라고 과장할 필요는 없다. 규칙 기반 템플릿으로도 일부 설명은 만들 수 있다. 이 프로젝트에서 LLM을 선택한 이유는 다양한 센서·이벤트·Vision 조합을 자연어 요약과 관리 포인트로 연결하기 위해서다. **템플릿 대비 만족도·시간 절감은 측정하지 않았으므로 성과 수치로 쓰지 않는다.**

## 3. 현재 코드 기준 흐름

```text
CronJob 요청 / 지정 날짜 배치 진입
  → 실행 시점 Data Generator Snapshot 조회 → 대상 재배지 해석
  → 공통 자료 1회 조회: 버섯 기준, 날짜별 알림 통계, 날짜별 사진
  → 재배지별 OWNER 식별
  → 기존 피드백 확인
       ├─ 있음: EXISTING 반환, 해당 대상의 Context 수집·Vision·LLM 생략
       └─ 없음: 재배 상세·센서 채널 통계·환경 유지율 수집
                 → 사진 있음: 기존 사진 분석 재사용 또는 다운로드·Vision·저장
                 → 사진 없음: hasVisionAnalysis=false
                 → 원본 Context Snapshot 보존
                 → LLM 전송용 복사본 정제·표시값 반올림
                 → Spring AI PromptTemplate + ChatClient
                 → 출력 검증
                 → 짧은 DB 트랜잭션: 피드백 + PENDING Outbox
  → 별도 Relay: 선점 → RabbitMQ 발행 확인 → PUBLISHED / 재시도 / FAILED
  → 팀 Notification: 소비·저장·구독 조건 확인·채널 전달
```

주의: 기존 피드백을 건너뛴다고 배치의 모든 호출이 0이 되는 것은 아니다. 공통 자료 조회와 OWNER 확인은 Processor의 기존 피드백 확인보다 먼저 실행된다. 또한 재배지별 반복은 현재 **순차 처리**이며 병렬 처리 성능 개선을 했다고 주장하지 않는다.

## 4. 데이터 의미를 먼저 맞춰야 했던 이유

| 데이터 | 현재 계약 | 해서는 안 되는 해석 |
|---|---|---|
| `feedbackDate` | Asia/Seoul 달력 날짜 | 모든 입력이 정확히 이 하루에 대응한다고 가정 |
| Data Generator Snapshot | 배치 실행 시점 활성 센서·현재 임계값 | 해당 날짜 과거 시점의 Snapshot으로 해석 |
| 센서 통계 | 조회 시점 rolling 24시간의 15분 평균 집계점 | 원시 측정값 하루의 실제 최솟값·최댓값이라고 표현 |
| 집계점 평균 | 반환된 집계점의 동일 가중 평균 | 원시 샘플 수로 가중한 전체 평균이라고 표현 |
| 환경 유지율 | 달력 날짜의 원시 측정값에 API 조회 시점 환경 설정 범위를 적용하는 계약 | 과거 설정 이력이 완전히 반영된 유지율이라고 표현 |
| 알림 통계 | 대상 날짜의 저장된 원본 이벤트 통계 | 알림 수 = 원시 센서 이탈 수 = 장치 작동 수라고 등치 |
| 사진 | 날짜별·재배지별 최대 한 장이라는 현재 Cultivation 응답 계약 | 하루 전체 사진·개체별 성장 추세를 종합했다고 표현 |
| 분석 시각 | 배치·재시도·기존 분석에 따라 달라질 수 있음 | 사진 촬영일과 분석일이 항상 같다고 가정 |

특히 `thresholdBreachAlertCount`는 현재 프롬프트 계약상 cooldown 이후 저장된 이탈 알림 수다. **현재 설정의 cooldown이 실제 운영 시점에 어떤 값이었는지는 별도 확인 대상**이다. 숫자 이름이 유사해도 의미를 바꿔 설명하면 안 된다.

## 5. 사건 노트

### A01. 센서 조회 계약의 필수 `unit` 전달 누락

- **문제/제약:** 동일 센서 타입이라도 섭씨·화씨 등 단위가 다르면 같은 채널이 아니다. 클라이언트가 필수 단위를 빼면 서버 계약과 맞지 않는다.
- **확인한 근거:** 개인 커밋 `cde30d4`(2026-09-04)에 `CultivationClient.getSensorTrend`의 `@RequestParam("unit")` 추가, 호출부 `channel.unit()` 전달, 테스트 stub 수정이 함께 들어 있다. [DF-E02]
- **판단:** 오류 응답만 우회할 것이 아니라 Feign 선언→호출부→테스트의 계약을 일치시킨다.
- **조치:** 채널 식별을 재배지·EUI·센서 타입·단위로 유지하고 요청에 단위를 전달했다.
- **검증:** 변경 diff와 현재 호출부·테스트 코드를 확인했다. 대화의 수정·재배포·재실행 이후 배치 성공 기록이 있다.
- **미확인/한계:** 이 작업에서 테스트를 재실행하지 않았다. 같은 시기에 Cultivation OOM 및 재시작도 있었으므로 배치 회복 전체를 이 수정 하나의 효과라고 단정하지 않는다.
- **배운 점:** Mock 테스트도 실제 외부 API의 필수 파라미터를 계약으로 검증해야 한다. 호출부끼리만 맞는 테스트는 누락을 놓칠 수 있다.

### A02. 내부 배치의 실행 사용자와 최종 사용자의 권한은 다르다

- **문제/제약:** 과거 로그에 재배 46 접근 거부가 있었다. 이후 사용자 제공 내부 조회에서는 OWNER가 존재하고 해당 사용자 헤더로 상세 조회가 성공했다.
- **근거:** 대화 증거와 현재 `CultivationOwnerService`, `DailyFeedbackQueryService`. [DF-E03, DF-H01]
- **판단:** 내부 배치용 소유자 식별과 브라우저 사용자의 접근 인가를 구분한다.
- **조치/현재 구조:** 내부 배치는 기존 ADMIN 계약으로 멤버를 조회해 OWNER 한 명을 요구하고, 대상별 데이터 수집에 그 ID를 재사용한다. 조회 API는 요청 사용자의 재배 접근 권한을 먼저 확인한 뒤 저장된 피드백을 읽는다.
- **검증:** 조회 서비스의 권한 선확인 순서 및 관련 단위 테스트가 존재한다. `aefcedf`는 개인 운영 조회 API 추가 커밋이다.
- **미확인/한계:** 과거 브라우저 403이 정확히 어느 사용자의 어떤 전달 경로 때문에 발생했는지는 당시 trace가 없어 확정하지 않는다. 내부 ADMIN 헤더는 신뢰된 내부 경계의 임시 계약이며 외부 인증 수단이 아니다. 2026-09-08 ADMIN 조회 보완(`6470579`)은 팀원 변경이다.
- **배운 점:** “데이터 생성 성공”과 “현재 로그인 사용자의 조회 성공”은 별도 검증이다.

### A03. ‘전날 보고서’의 데이터가 모두 같은 시간 범위는 아니었다

- **문제/제약:** 발표 초안은 전날 재배지와 하루 통계를 한꺼번에 설명했지만 현재 API의 시간·집계 기준은 서로 다르다.
- **근거:** Batch/ContextCollector, CultivationClient의 Trend 계약, 통계 계산 코드와 프롬프트 시간 규칙. [DF-E04]
- **판단:** 서로 다른 기준을 감추고 하나의 하루 인과관계로 설명하지 않는다.
- **조치/현재 구조:** Context에 날짜와 Snapshot 시각을 구분하고, 프롬프트에서 rolling 통계·달력 날짜 유지율·현재 임계값을 별도로 설명하도록 한다. 타입과 단위가 일치할 때만 현재 설정 기준 참고 비교를 허용한다.
- **검증:** 현재 코드·프롬프트에 기준이 명시되어 있다. 통계 계산기는 채널 일치와 집계점 수를 검사한다.
- **미확인/한계:** 과거 임계값 이력이 없어 변경 전후 효과를 복원할 수 없다. 호출 시점이 이동하는 Trend API라 재실행 입력이 완전히 같다고 보장할 수 없다.
- **배운 점:** 데이터의 단위뿐 아니라 시간 창, 집계 수준, 분모도 API 계약이다.

### A04. LLM 입력 정제와 원본 근거 보존을 분리했다

- **문제/제약:** Context에는 내부 식별자·사진 연결 정보처럼 외부 LLM 설명에 불필요한 값이 포함될 수 있다. 추후 원인 추적에는 원본 수집 근거가 필요하다.
- **근거:** `DailyFeedbackProcessor`의 Snapshot 생성, `DailyFeedbackPromptContextSanitizer`, GenerationService. [DF-E05]
- **판단:** DB 근거 Snapshot과 외부 전송용 Context를 같은 객체로 수정하지 않는다.
- **조치:** 새 object/array를 만들어 내부 ID·역할·URL 관련 필드·모델/좌표 메타데이터 등을 제거하고, 보존 문자열에 연결정보가 남으면 거부한다. 센서 통계 표시값만 복사본에서 반올림한다.
- **검증:** 원본 불변성, 중첩 구조, 금지값 및 별칭 관련 테스트가 존재한다.
- **미확인/한계:** 모든 개인정보·프롬프트 인젝션을 완전 차단한 일반 DLP가 아니다. `deviceEui`는 채널 구분을 위해 남는다. 저장용 Snapshot 접근·보존 정책도 별도 관리가 필요하다.
- **배운 점:** 보안 요구와 재현 가능한 기록 요구를 서로 다른 데이터 경계로 설계할 수 있다.

### A05. LLM에 형식을 요청하는 것과 검증하는 것은 다르다

- **문제/제약:** 모델이 공백 응답, 다른 제목, 코드 블록 또는 내부 정보를 포함한 결과를 줄 수 있다.
- **근거:** `DailyFeedbackGenerationService`, `DailyFeedbackOutputValidator`, 두 프롬프트. [DF-E06]
- **판단:** 프롬프트 지시만 믿지 않고 저장 전에 결정론적 검증을 적용한다.
- **조치:** Spring AI `PromptTemplate`으로 시스템 지침과 Context를 조합하고 `ChatClient`로 호출한다. 다섯 Markdown 섹션의 순서·중복·본문 유무와 금지 내용을 검사한다. Gemini 호출 또는 출력 검증 실패 시 선택적 Ollama ChatClient Bean이 있을 때 한 번 fallback한다.
- **검증:** 출력 제목·빈 본문·금지 주소·fallback 동작 관련 테스트가 존재한다.
- **미확인/한계:** 현재 런타임에서 fallback 모델이 실제 활성화됐는지 이번에는 확인하지 않았다. Validator는 문장의 수치 일치·병해 설명 충실도·환각을 전부 검증하지 않는다. “검증 통과=사실 정확성 보장”이 아니다.
- **배운 점:** 출력의 구조적 유효성, 근거 일치, 사용자 유용성은 각각 다른 품질 기준이다.

### A06. 사진 없음, 미탐지, 불확실, 분석 실패를 구분했다

- **문제/제약:** 사진이 없는 사용자가 있고, 사진이 있어도 다운로드나 모델 호출이 실패할 수 있다. 모델은 미탐지나 낮은 신뢰도를 반환할 수도 있다.
- **근거:** `DailyVisionAnalysisService`, `VisionRelayService`, BatchService. [DF-E07]
- **판단:** 수집 실패를 정상 판정 또는 사진 없음으로 바꾸지 않는다.
- **조치:** 사진 없음은 Vision 없이 센서 기반 피드백을 생성한다. 사진이 있는 경우에는 기존 분석을 조회하거나 다운로드·모델 호출·응답 검증 후 저장한다. 실제 실패는 해당 재배지 실패로 전파되고 배치는 다음 대상 처리를 계속한다.
- **검증:** 사진 없음 Optional, ID 불일치, 응답 상태/확률, 기존 결과 재사용 및 실패 격리 관련 테스트가 존재한다.
- **미확인/한계:** 현재 흐름에서 사진이 있는데 분석이 실패한 재배지는 신규 피드백 생성도 실패한다. 다른 재배지를 계속 처리한다는 뜻이지 해당 재배지의 센서 전용 피드백을 무조건 저장한다는 뜻은 아니다. 공통 사진 목록 조회가 실패하면 배치 전체 공통 수집 실패가 된다.
- **배운 점:** `null`, 결측, 실패, 불확실은 서로 다른 도메인 상태다.

### A07. 불필요한 이미지·LLM 호출을 줄이되 재분석 요구와 구분했다

- **문제/제약:** 배치 재시도 시 이미 저장한 결과를 다시 만들면 비용과 지연이 늘고 내용도 달라질 수 있다. Presigned URL에는 만료시간이 있다.
- **근거:** Processor의 기존 피드백 반환, VisionRelay의 사진 ID 재사용, Batch의 공통 조회 순서. [DF-E07, DF-E08]
- **판단:** 완료한 결과는 재사용하며, 사진 분석은 다른 필수 데이터가 준비된 후 수행한다.
- **조치:** 배치 공통 자료를 각각 한 번만 가져오고 사진 목록은 마지막에 가져온다. 동일 사진 ID 분석 기록과 동일 재배지·날짜 피드백을 먼저 조회한다.
- **검증:** 기존 피드백 시 의존 서비스 호출 생략, 사진 결과 재사용 테스트가 있다.
- **미확인/한계:** API 호출 감소량·비용·지연 개선율은 측정하지 않았다. 모델을 교체해도 같은 사진의 기존 결과가 재사용될 수 있으므로 버전별 강제 재분석 정책은 별도 필요하다. 대표 사진 선정 알고리즘을 AI 서버가 구현했다고 표현하지 않는다.
- **배운 점:** 멱등 재시도와 의도적인 재생성은 서로 다른 기능이다.

### A08. 느린 외부 호출과 짧은 DB 저장의 경계를 나눴다

- **문제/제약:** 외부 API·Vision·LLM 응답을 기다리는 동안 DB 연결을 계속 점유하지 않도록 해야 했다. 동시에 같은 날짜를 저장할 가능성도 있었다.
- **근거:** Processor/Batch `NOT_SUPPORTED`, AtomicWriter `REQUIRES_NEW`, PersistenceService의 경쟁 처리, 엔티티 UNIQUE 선언. [DF-E08]
- **판단:** 외부 수집·생성은 트랜잭션 밖에서 하고, 최종 DB 저장만 별도 Bean의 짧은 트랜잭션으로 수행한다.
- **조치:** 재배지·날짜 선조회 후 저장하고, 동시 저장 충돌이면 AtomicWriter 롤백이 끝난 뒤 기존 행을 다시 찾는다. 기존 행이 없으면 무관한 제약 오류일 수 있으므로 원래 오류를 던진다.
- **검증:** 정상 저장·경쟁 충돌·무관한 DB 오류·트랜잭션 선언 관련 테스트가 존재한다.
- **미확인/한계:** 소스의 UNIQUE 선언과 mocked 단위 테스트만으로 운영 DB 제약 설치·동시성 실증을 새로 증명한 것은 아니다. 동시에 모두 선조회를 통과하면 외부 호출은 중복될 수 있으며 저장 멱등성이 호출 exactly-once를 보장하지 않는다.
- **배운 점:** 사전 조회는 최적화이고, 동시성의 최종 판단은 DB 제약에 맡겨야 한다.

### A09. 피드백 저장과 알림 발행 사이의 틈에 Outbox를 적용했다

- **문제/제약:** DB 저장 후 RabbitMQ 직접 발행이 실패하면 결과는 있는데 알림이 없는 상태가 된다. 반대로 발행만 먼저 성공하면 없는 피드백으로 안내할 수 있다.
- **근거:** 개인 `bfff1c2`, AtomicWriter, Outbox 엔티티·Claim·Relay·Recovery. [DF-E09]
- **판단:** DB와 Broker를 하나의 트랜잭션이라고 가정하지 않고, 발행해야 할 의도를 DB에 함께 기록한다.
- **조치:** 피드백과 `PENDING` Outbox를 같은 DB 트랜잭션으로 저장한다. Relay가 `FOR UPDATE SKIP LOCKED`로 선점하고 `SENDING` 전이·시도 횟수 증가를 커밋한 뒤 네트워크 호출한다.
- **검증:** 저장 위임·발행 성공·재시도·최대 시도·복구·상태 기록 실패 관련 테스트가 존재한다. 과거 사용자 제공 자료에서는 신규 11건 모두 PUBLISHED가 확인됐다.
- **미확인/한계:** 장애가 영구적으로 지속되면 FAILED가 남는다. Outbox는 무조건 최종 전달을 보장하는 마법이 아니며 모니터링과 수동 복구 정책이 필요하다.
- **배운 점:** ‘성공/실패’ 한 값보다 ‘무엇을 완료했고 다음에 무엇을 해야 하는가’를 저장하는 것이 중요하다.

### A10. Broker ACK, 라우팅, 소비, 최종 사용자 수신은 서로 다르다

- **문제/제약:** `convertAndSend`가 정상 반환했다고 실제 사용자에게 알림이 도착했다고 볼 수 없었다.
- **근거:** Producer의 Confirm Future/ReturnedMessage 검사, correlated·returns·mandatory 설정. [DF-E10]
- **판단:** AI 측 발행 완료는 Broker 발행 확인과 미반환 조건까지만 뜻하게 한다.
- **조치:** 발행 시도별 `publicationAttemptId`를 CorrelationData에 넣고 ACK 및 returned message 없음 조건을 모두 만족할 때 정상 반환한다. NACK·return·timeout은 Relay 재시도 대상으로 전파한다.
- **검증:** ACK, NACK, unroutable return, timeout, 비동기 오류, interrupt 테스트가 존재한다.
- **미확인/한계:** ACK+미반환은 Notification DB 저장·사용자 수신을 확인한 것이 아니다. 잘못된 다른 큐로의 라우팅까지 업무적으로 검증하는 수단도 아니다. 소비자 ACK와 publisher confirm을 혼동하면 안 된다.
- **배운 점:** 전달 단계마다 확인 가능한 성공 범위를 이름과 로그에 명확히 표현해야 한다.

### A11. 발행 성공 후 프로세스가 종료되면 같은 이벤트가 다시 갈 수 있다

- **문제/제약:** Broker에는 전달됐지만 Outbox PUBLISHED 저장 전에 종료되거나 DB 기록이 실패할 수 있다.
- **근거:** Relay의 상태 기록 실패 처리, Recovery의 stale SENDING 복구, 결정적 eventId Factory. [DF-E11]
- **판단:** 중복 가능성을 부정하지 않고 `at-least-once`와 소비자 멱등 처리로 설계한다.
- **조치:** 발행 성공 뒤 DB 상태 저장 실패는 SENDING으로 남겨 복구한다. 같은 재배지·날짜는 같은 eventId를 사용하며, 발행 시도 ID는 별도로 증가한다. 오래된 SENDING은 횟수에 따라 PENDING 또는 FAILED로 전이한다.
- **검증:** PUBLISHED 기록 실패 후 SENDING 유지, retry/backoff, stale recovery 테스트가 있다.
- **미확인/한계:** Notification의 eventId 중복 저장 방지는 팀 서비스 책임이다. 외부 Discord/Telegram 전송 뒤 소비자 DB 기록 전 실패 같은 추가 틈까지 exactly-once라고 단정할 수 없다.
- **배운 점:** 같은 이벤트의 정체성(eventId)과 개별 네트워크 시도(Correlation ID)를 분리해야 늦은 응답과 재시도를 구분할 수 있다.

### A12. ‘정상 발행’ 기록과 ‘내가 알림을 못 받음’이 동시에 나타났다

- **문제/제약:** 과거 배치는 성공했지만 사용자는 Telegram 알림을 보지 못했다. 처음 필터링한 로그에는 일부 발행만 보였다.
- **근거:** 2026-09-04 대화의 배치 응답·Outbox 표·Notification 표·delivery 표. [DF-H01]
- **판단:** 로그 일부만으로 전체 누락을 결론내리지 않고 저장 단계와 구독 조건을 각각 확인한다.
- **조치/관찰:** Outbox 11건 PUBLISHED, 대응 Notification 11건 저장이 이미지로 확인됐다. delivery 화면에서는 한 재배지 Telegram SENT와 나머지 조인 결과 null이 보였다. 사용자는 본인이 Telegram 구독자가 아니라고 설명했다.
- **검증:** 관찰한 단계까지의 통합 근거는 있다. SENT 기록은 발송 제공자 응답 기록이지 수신자가 실제 읽었다는 증거는 아니다.
- **미확인/한계:** 나머지 null 모두가 구독 없음 때문인지 이 자료만으로 확정할 수 없다. 당시 쿼리 전체·구독 설정·원본 로그가 없고 현재 운영 상태도 확인하지 않았다.
- **배운 점:** 배치 생성, Outbox 발행, Notification 저장, delivery 발송, 화면 조회를 나누어 추적한다.

### A13. 팀원이 ‘Vision 피드백 내용이 부실하다’고 평가했다

- **문제/제약:** 탐지·건강 상태 분류는 동작하더라도 사용자에게 “그래서 무엇을 확인해야 하는가”가 충분히 설명되지 않을 수 있다.
- **근거:** 사용자의 팀원 피드백 전달. 현재 Vision 분석 JSON은 Context로 유지되고 프롬프트 정제 후에도 상태·수·점수·경고가 남는다. [DF-E05, DF-E07, DF-E12]
- **판단:** 모델 정확도 문제, LLM의 결과 활용 문제, 프론트 근거 제시 문제를 먼저 구분한다. 실제 부실 문장이나 입력·출력 쌍이 없어 원인 확정은 하지 않았다.
- **제안한 개선:** 결과를 분석 사진/영역·상태의 의미·다음 확인 행동으로 구성한다. 불확실/미탐지/병해 의심별 설명을 구분하고, 예시 입력과 사람 평가 기준을 마련한다.
- **검증:** 이 기록에서는 개선 구현·사용자 평가를 수행하지 않았다. **개선 제안 단계**다.
- **미확인/한계:** 현재 모델은 병명 확진, 병변 위치, 성장률, 수확 시점을 제공하지 않는다. 문장을 늘리려고 갈변 위치나 과습 원인 등을 생성하면 안 된다. 탐지 수와 품종별 건강 분류로 개체별 병해 수를 산출할 수도 없다.
- **배운 점:** 출력 형식을 지키는 모델과 실질적으로 도움 되는 피드백은 다르며, 근거를 벗어나지 않는 설명 품질 평가가 필요하다.

## 6. 남아 있는 한계와 다음 단계

1. **기간 정합성:** 지정 날짜 통계 API 및 과거 임계값 이력을 마련하기 전에는 rolling 24시간과 달력 날짜를 계속 구분해야 한다.
2. **품질 평가:** 사진 없음·정상·병해 의심·불확실·미탐지 등의 고정 사례로 근거 일치, 유용성, 과잉 단정 여부를 평가한다. 아직 점수화된 결과는 없다.
3. **재생성 정책:** 같은 날짜 결과 재사용과 새 모델/새 프롬프트 재생성을 구분하는 버전·승인 정책을 검토한다.
4. **운영 증거:** 실제 배포 revision, DB UNIQUE, CronJob 중복 방지 정책, Outbox FAILED·오래된 SENDING 모니터링을 별도로 확인한다. CronJob 사용만으로 정확히 한 번 실행을 보장하지 않는다.
5. **사진 정책:** 현재 날짜별 최대 한 장 계약의 선택 기준과 누락 영향을 Cultivation 담당자와 확인한다.
6. **팀 계약:** ADMIN 경계, 이미지 허용 origin, Notification 이벤트·URL 계약 변경 시 양측 테스트로 재검증한다. 9/14의 다른 작업명만으로 미반영 변경을 완료 사실로 넣지 않는다.

## 7. 포트폴리오·자소서·면접에 재사용할 문장

### 이력서용

> Spring AI 기반 일일 피드백의 데이터 수집·입출력 검증·멱등 저장을 구현하고, Outbox의 발행 확인·재시도 흐름을 연결했습니다.

### 포트폴리오용 문제 해결 요약

> 센서 조회 과정에서 필수 단위 파라미터 누락을 확인해 Feign 선언, 호출부, 테스트를 함께 수정했습니다. 또한 외부 API·LLM 호출과 DB 저장의 트랜잭션 경계를 분리하고, 피드백과 발행 대기 이벤트를 같은 DB 트랜잭션에 보존하도록 구성했습니다. 당시 통합 확인에서는 대상 21건 중 신규 11건·기존 10건·실패 0건과 신규 Outbox 11건의 발행 상태를 확인했습니다. 이 결과는 한 번의 확인 사례이며 장기 운영 안정성 지표는 아닙니다.

### 자소서 STAR 소재 — 외부 계약을 끝까지 확인한 경험

- **상황:** 여러 서비스의 자료를 모아 일일 피드백을 생성하는 과정에서 조회 실패와 생성·알림 상태를 함께 확인해야 했다.
- **과제:** 내 AI 서비스 내부만 수정하는 것이 아니라 외부 API의 사용자 식별·단위·시간 기준을 맞춰야 했다.
- **행동:** API 선언과 실제 호출 파라미터를 비교하고, 단위 누락을 호출부와 테스트까지 함께 수정했다. 결과 추적도 배치·Outbox·Notification 단계로 나눴다.
- **결과:** 과거 배치와 DB 화면에서 생성 및 발행·저장 결과를 확인했다. 전체 장애를 단일 수정의 효과로 과장하지 않고, OOM 재시작 등 동시 변경도 기록했다.
- **배움:** 통합 문제는 코드 한 곳의 성공 여부보다 서비스 경계의 계약과 단계별 근거로 판단해야 한다.

이 문장을 본인의 기억과 코드 설명 능력에 맞게 수정한다. “직접 전부 작성”, “환각 완전 제거”, “정확히 한 번 전달”, “장애 100% 해결”이라는 표현은 사용하지 않는다.

### 면접에서 준비할 질문

- DB 저장과 Broker 전송을 왜 한 `@Transactional`로 끝낼 수 없나?
- `NOT_SUPPORTED`와 `REQUIRES_NEW`를 다른 Bean에서 사용한 이유는?
- 선조회가 있는데 UNIQUE 제약도 필요한 이유는?
- RabbitMQ가 ACK했는데 왜 메시지가 다시 발행될 수 있나?
- `eventId`와 `publicationAttemptId`의 목적은 어떻게 다른가?
- 사진 없음과 분석 실패는 배치 결과에서 어떻게 달라지는가?
- LLM 출력 검증이 확인하는 것과 확인하지 못하는 것은?
- 최근 24시간의 15분 평균 집계점 최소값이 하루 원시 최소값과 다른 이유는?
- 모델/프롬프트를 바꾼 뒤 기존 결과를 다시 만들려면 무엇을 바꿔야 하나?
- 팀원의 기반 기능과 내 구현 범위를 어떻게 구분했나?
